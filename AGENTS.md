# Rewrite contributor guide

This is a separate Git repository and Go module. `docs/dev/generic-config-alternative.md` is the approved named-session/config-source contract and supersedes the selection/config sections of `docs/dev/rewrite-plan.md`. The latter retains the other runtime contracts. `docs/dev/migration-plan.md` describes a separate removable utility, never startup behavior.

- Support Linux only. Use Linux process identity, terminal, and locking APIs directly; do not add macOS/Windows fallbacks or portability abstractions.
- Run `make test` after code or behavior-affecting configuration changes. Documentation-only changes, including proposals and `AGENTS.md`, do not require tests or builds unless explicitly requested. `make check` also formats, race-tests, and builds.
- `make` prefers this repository's `.tools/go`, then the parent's toolchain. Use `make install-go` for a standalone checkout.
- Development builds are named `devbox-neo`. Their default home is `~/.devbox-neo`; `--home` takes priority over `DEVBOX_HOME`. The conventional old `~/.devbox` and its descendants are rejected even when explicitly selected. Container/session names use `devbox-<folder>-<12-hex-hash>.<local-name>`, hashing canonical workspace bytes, NUL, and exact local name. Local names match `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` without normalization; Docker ownership labels and image tags retain the separate `devbox-rewrite` namespace. Names never prove ownership. This naming change requires a clean session reset; do not add automatic migration or adoption. Tests must use temporary homes, never the user's current home or Docker resources.
- Keep lifecycle generic: no harness-name branches, old-schema readers, or config reloading in execution. Pi's built-in launch defaults to `--tui-mode fullscreen`; later harness arguments can override it. Pi's managed installer runs as `devuser` in image-only `/home/devuser/.pi/image/`, not in the mounted `.pi/agent` store or `.local` cache; keep its binary on the image PATH and the `.pi` parent writable.
- Use `commanderror.Error`/`Step` for actionable failures and preserve their causes. `cli.Execute` owns error rendering; human output uses short `Error:` messages, separate target context, and labeled `Step.Reason` commands. Keep codes/operation metadata in JSON. Generic creation hints show `create <folder>` rather than replaying unrelated invocation flags. Missing-session and config-owner hints retain the entered target spelling; filesystem identity stays canonical. Exact session/transfer selectors remain intact. Mark sequential/alternative reasons with `Then`/`Or`; do not embed next-command strings into errors or render them inside handlers. Missing-file control flow must remain distinct from invalid state; use `errors.Is` when consuming wrapped lookup errors. The executable remains `devbox-neo`; a doctor command is not planned.
- Images have one ownership contract: `base_image` → prepared Devbox user/runtime → ordered source Dockerfiles → harness installation/validation. Custom stages extend `DEVBOX_BASE`; layer ancestry verifies the supplied base. Each stage retains its own captured context/ignore rules. Restore USER/HOME/workdir/shell between stages while preserving custom PATH. Build arguments are `DEVBOX_BASE`, `DEVBOX_USER`, `DEVBOX_USER_HOME`, `DEVBOX_WORKSPACE`, `DEVBOX_UID`, and `DEVBOX_GID`. Conflicting upstream users fail; do not rename accounts or recursively chown content. Do not reintroduce `Dockerfile.full` or a user-owned runtime branch.
- Derive managed harness mount parents through `Definition.MountParents`. Image-only ancestors belong in the mandatory runtime layer; bind-backed ancestors belong in recorded create/start preparation. Do not patch harness names, recursively chown mounted state, or recreate missing durable roots.
- Session mutation requires external operation locks; labels, not names, prove Docker ownership. New-session creation is explicit: `create <folder>` prepares and leaves a stopped environment without launching its harness; `open`/`start` require an existing session and never create a new one. Container settings belong in sparse explicit config sources. `create` requires a local name and at least one ordered config reference, prompting only in a terminal; it never sets a default. Folder lookup uses `--name` or a saved default, without implicit sole-session selection. `create`/`recreate` accept selection and operational flags only. There is no workspace read-only setting. `open` accepts continuation and invocation-only harness arguments. Explicit `start` records manual keep-running intent until `stop`, across attachments and reboot; Docker restart policy is Devbox-owned (`unless-stopped` for manual, `no` for automatic). Without manual intent, the last attached command stops the container. There is no `on_exit` config/flag/lease policy. Both open/start retain recorded missing-container recovery. `create` never overwrites an existing session.
- The saved session is the top-level environment model. `list`, `status`, `copy`, and `delete` live at the root; `status <target>` combines saved details, live leases, and desired changes without hiding details on config errors; there is no separate `show` command; do not restore a `session` group or container-only list/status. List and bulk status retain missing-container sessions and report unmatched installation-owned containers separately, including in JSON. Corrupt records remain session diagnostics. `delete` holds the complete operation-lock set across container and optional saved-state deletion. Mutually exclusive `--container` and `--session` flags select runtime-only versus whole-environment deletion and skip prompts. Without scope, interactive deletion asks about each phase; scripts/JSON/dry runs require explicit scope. `--force` only allows disruption of container commands; saved-state deletion still requires idle leases. Delete owns intersecting age/orphan/stopped/all filters, rechecked under lock before mutation. Do not restore `reset`, `prune`, `--yes`, `--include-session`, or the harness `reset_preserve` field. No silent combined wipe or command aliases.
- Managed config is authoritative. Ordinary managed files replace live edits and obsolete managed paths are removed; shared JSON owns only declared keys and preserves the rest. Never wipe unmanaged files/history to synchronize. `app.startAccess` owns ordinary stopped-to-running preparation for open/start/shell/exec/ssh; resolve once, validate backing roots, synchronize compatible recorded harness layouts, then start. Running access does not sync, and invalid participating config blocks startup. Creation/recreation and transfer destination creation sync before materialization. Rollback and committed-transfer recovery retain recorded transaction behavior, without reloading desired config. Incompatible definitions still require recreation. Do not advance applied runtime inputs/launch settings until preparation succeeds.
- `environment.Inputs` is the shared source for aggregate fingerprints and detailed drift reasons. Session record schema 5 requires its complete applied snapshot, committed `inputs.sources` directories, and structurally valid relative/fixed desired `sources` (which may temporarily be empty for repair); image stages and setup/before-open hooks are ordered inputs; older records require a clean development reset, not compatibility readers or migration. Keep image/container inputs fixed until creation/recreation commits, and advance runtime inputs with their fingerprint through `Record.ApplyRuntime`. Never infer old inputs from current source files or add independent drift rules to CLI rendering.
- `app/transfer.go` owns the transfer state machine. The CLI exposes `copy` and `copy --move`, without `clone`/`relocate` command aliases; internal journal/JSON modes and harness capability fields remain `clone`/`relocate`. One external `state/transfers/<source-container>.json` journal reserves both endpoints; ordinary mutations use `Locked.Load` to reject pending transfers. Journal schema 2 pins named endpoints. `--as` selects the destination local name, otherwise retain the source name; an omitted destination folder uses the source workspace. Rebase only relative config references, never copy config/workspace files. Retry uses the journal's exact endpoints without reloading config after commitment. Copy leaves defaults untouched; move clears only a matching source default through the shared saved-state removal path. Never repeat state copying after destination commitment, or delete the journal with source state.
- `config.Reference` preserves explicit relative/fixed intent; relative CLI arguments first resolve against the invoking cwd, then save relative to the canonical workspace. Bare names use `<selected-home>/configs`; fixed references stay absolute across transfers. `ResolveReferences` is the absolute-source boundary and rejects duplicate canonical directories. `artifact` composes built-in defaults followed by all explicit sources, without global settings, discovery, or cutoffs. `app.Locate` reads identity/default state, not config. Lifecycle operations load desired references under the operation lock; source edits preserve identity and applied inputs. Configured `harness_args` requires its own harness, and mismatching sources contribute no arguments.
- `resource` owns config-directory creation, settings, missing optional artifacts, and `config list`'s read-only inventory of named directories under the selected home's `configs/`; path-based configs outside it have no registry. Include invalid/incomplete directories without requiring Docker or host expansion. `config delete` removes only direct named directories, never symlinks or arbitrary paths; confirm unless `--force`, which never bypasses current saved desired/committed reference checks. Share the complete, sorted usage report with the interactive directory editor and blocked-deletion error; show each session once without exposing desired/committed labels, and preserve known users when the report is incomplete. Invalid records and pending transfers block deletion; session creation/source edits may still race because they do not acquire the config lock. Existing `config.json` rejects creation before prompts; repeat the check under the canonical owner lock and claim the file without replacement before adding artifacts. Existing directories without that file are allowed. Harness-file generation is independent of the persistent harness setting. Keep `config create`, `config edit`, session `create`, `config sources`, and `set` as separate menu entry points. Settings use `SetConfigField` and same-field conflict checks; source edits compare session ID and displayed sources under the operation lock. Completed edits save immediately; pending creation choices do not. Use canonical line input, `:back`, shared numbered controls, selection summaries, and color-independent selected markers. Directory dashboards show only that source over defaults; combined inspection is read-only and consumes `artifact.Trace.EntrySources`.
- Folder defaults belong to `store`: `state/workspaces/<SHA-256-workspace-bytes>.json` records full name plus durable ID, or null. Workspace locks are stable and external. Acquire session operation locks first, then workspace locks; never reverse that order. Default resolution releases the workspace lock before acquiring a session lock and verifies the selected ID. `removeSavedSession` clears a matching default before deleting state; container-only deletion does not. Malformed default state cannot hide inventory or block exact session lookup.
- `setup.sh` and `before-open.sh` run in explicit source order as separate processes, stop on failure, and do not roll back workspace effects. Import source copies use `artifact.SourceTree` and preserve expressions; previews bind one source path without changing participation.
- Shell completion is read-only: bypass `store.Open` and locking record readers; never seed state or create locks on Tab. Name suggestions are lookup hints, not ownership proof. Use bounded installation-filtered Docker inventory only for live container targets, and tolerate unavailable sources without diagnostics. Generated scripts register existing `dbx` shortcuts without defining or changing them.
- Terminal display metadata is invocation-local: capture the allowlist in the CLI, supply defaults only to the temporary creation plan, and refresh it through attached-command exec overrides. Keep it out of desired configuration, fingerprints, and saved env-source references; do not change recorded shell argv or import host dotfiles.
- Never persist env/auth values in session records or print them in diagnostics. Sensitivity is by field: names, paths, networks, argv, and ordinary settings are public, including `${env:...}` substitutions. Config env recovery uses exact source-entry references and keyed fingerprints; public creation accepts no env overrides, and persistent env values come from configuration source references.
- `ssh <target> <destination>` is foreground user-authenticated connection sharing, not a shell into the container. Container master is the default; invocation-only `--host-master` starts a dedicated host master and prints the agreed host/network-access warning before authentication. Honor normal SSH configuration, including ProxyJump, keys, agent and X11 forwarding; never force forwarding off, copy credentials/config, adopt personal masters, or silently switch modes. `app.SSH` uses `startAccess` and the common `attachRun` lease owner. `sshshare` owns per-invocation control sockets/config and the flock-backed supervisor: owner loss must terminate the actual master, including before authentication. Publish only after socket readiness; generated clients must fail without a fresh-login fallback. `/devbox/ssh` is a private per-environment mount from `sessions/<name>/runtime/ssh`, excluded from transfers and runtime asset permission changes. Missing mounts require explicit recreation, not migration or late mount injection. No identity/detach flags, reconnect daemon, credential provisioning, or separate disconnect command. SSH status output must respect Docker's active raw-terminal mode and restore the host terminal on return. Normalize only expected foreground interruption before joining cleanup failures; successful disconnect prints `Disconnected.`, while real failures and deadlines remain visible.
- Runtime guidance is embedded from `docs/` and `internal/assets/`; built-in Pi/OpenCode `skills/devbox/SKILL.md` defaults link to `/devbox`. Artifact setup must leave this skill inherited, not copy it into config directories; explicit user overrides remain supported. Keep these inputs and network-fact paths aligned when container behavior changes.
- Keep tests and guide/reference/architecture docs aligned. Record unpassed acceptance gates honestly in `docs/dev/progress.md`.
- Migration logic belongs only in dedicated `migrations.go` / `*_migrations.go` files inside the removable migration package. `app.CreatePrepared` is the normal destination-creation API shared by transfer and import: the caller holds the operation lock and owns prepared-state publication/recovery. Do not add migration markers to ordinary records or make runtime packages read migration journals.

## Documentation writing

Organize docs around the reader's next action, not the implementation's inventory of features. User docs are not an implementation changelog.

### Keep the tiers distinct

- **Guides** (`docs/src/guides/`): teach practical workflows, starting with simple usage and building toward advanced features. Introduce the main concepts as they become useful. Keep schemas, locking, fingerprints, transaction mechanics, and exhaustive edge cases out of the walkthrough.
- **Reference** (`docs/src/reference/`): provide concise lookup material—command syntax, flags, fields, defaults, validation, paths, and exact behavior. Prefer focused tables and short rules over repeated explanatory paragraphs.
- **Architecture** (`docs/src/architecture/`): explain component ownership, data flow, lifecycle, invariants, synchronization, locking, recovery, and design tradeoffs in detail. Use diagrams where they clarify structure or ordering.

### Write guides for someone learning the tool

- Teach one concept or action at a time. Explain what a command does, where to run it, and what happens next. Separate distinct actions into their own examples; do not put `shell` and `exec` in one block as if they were a sequence. Explain that `shell` opens an interactive terminal inside the container and how to return to the host.
- Explain notation before relying on it: `<folder>` is a placeholder for a project path, and `.` means the current folder. Do not assume a reader already knows shell conventions.
- Lead with the interactive CLI wherever a menu exists. Show `config create base`, `config edit base`, `create .`, or `set .`, then explain the relevant menu choice. Keep explicit `--harness`/`--artifact` recipes in reference or advanced automation material, not basic setup.
- Use the simplest command that serves the current step. Show `list`, not `list --sort last-active`, when teaching listing. Introduce options only when the workflow needs them; useful shorthand such as `--continue` / `-c` can be shown together when teaching that feature.
- Use **harness** consistently for the coding tool Devbox launches, such as Pi or OpenCode, and for its configuration, launch options, and saved state. Define it plainly on first introduction. Do not substitute “agent” to sound approachable; reserve that word for the actual agent acting through the harness or established terms such as SSH agent forwarding.
- Include the practical steps needed to finish a task. For shell setup, show what to put in `~/.bashrc` and how to reload it, rather than merely saying to keep a binary on PATH. Use neutral checkout placeholders such as `/path/to/devbox`, not a contributor's personal path or the repository's nested development layout.
- Give a guide one **Next** destination, not several competing next steps. Other reference links can appear beside the topic they explain.

### Remove noise without hiding real constraints

- Describe the supported behavior positively. Do not explain obsolete features or nonexistent modes that the reader has never encountered, such as “There is no Dockerfile.full mode.”
- Keep rewrite status, delivery checkpoints, migration history, and acceptance-gate progress in `docs/dev/`, not user-facing introductions or walkthroughs. State real prerequisites and current safety constraints where they affect the task, without wrapping them in development-status chatter.
- Keep shared facts consistent across tiers, but do not repeat the same implementation detail everywhere. Link to the appropriate depth instead. New features should receive space proportional to comparable existing features.
- Verify examples and menu behavior against the CLI. Keep navigation, links, terminology, and embedded docs aligned. When feedback exposes a writing problem, check adjacent examples for the same pattern rather than fixing only the quoted sentence.
